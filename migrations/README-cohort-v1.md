# Cohort v1 SQL handoff (draft; no database has been changed)

Files: `20261002_cohort_v1_up.sql` and `20261002_cohort_v1_down.sql`. Both are transactional. The down script deliberately aborts if second-term or suspended data exists, since returning to single-term RLS would disclose that data. In that case restore from the pre-migration database backup or prepare a data-preserving forward repair; do not force the down script.

## Technical choices

1. Add `cohort` to each of `team_meetings`, `trade_ledger`, and `reviews`. The existing team number remains local to a cohort; `(cohort, team_id)` is the logical team key. This changes fewer app paths than adding a global teams table. Team queries and writes must be filtered by both fields. The RLS rules enforce both fields regardless of frontend filters.
2. Add `all_cohorts boolean` to `course_materials`. Ordinary materials match one `cohort`; a common item is visible to every active cohort. This matches the requested pre-class shared material use case, with one UI checkbox. Upgrade to a mapping table only if specific subsets of terms become necessary.

`flow_configs` currently has a unique `group_id`. The migration changes uniqueness to `(cohort, group_id)`. **The updated app action must deploy with the SQL**: publishing now reads the current cohort and upserts on `cohort,group_id`; unpublishing filters by both. Without this app change, a second-term publish can overwrite or conflict with first-term settings. The SQL guard requires the old unique constraint to be present. The existing three team forms also need a cohort value from the active member; current column defaults cover inserts, while their update/delete paths must add cohort filters. Roster writes need cohort and status controls in the UI; those are outside this B/C handoff.

After rebasing onto the merged stage-six custom-chain implementation, `group_id` remains `sanitizeSplitConfig(payload).group`. For a custom chain this is its validated `c_…` chain ID, so the unique key is `(cohort, chain ID)`; the UI uses `resolveGroup(state)` for the same ID when choosing the current published config.

`course_videos` cohort isolation is included here to satisfy AC3: the **ten** existing links seen in the 2026-10-03 production read-only catalog check migrate to `2026-1`, and `elite_videos_select` applies the same cohort/common-material logic. Video v2 retains playback and per-video targeting UI. **Known AC8 limit accepted by the product manager:** suspension stops issuing new signed URLs immediately; URLs already issued by the materials page remain valid until their one-hour expiry. AC8 verification measures immediate denial of metadata/new URL issuance and records this one-hour existing-link window.

**Storage owner dependency:** production's `elite_materials_storage_select` checks `is_enrolled()` only, so a second-term member who already knows a first-term file path may be able to request a fresh signed URL directly from Storage. The policy belongs to `supabase_storage_admin`; catalog checks show the usual migration role `postgres` is neither superuser nor a member of that owner role. The present up/down SQL deliberately does not edit that policy. Before declaring AC3's file access secure, arrange an owner-authorized Storage policy update that also checks the referenced `course_materials` row against `my_cohort()` / `all_cohorts`, and test signing a known first-term path as a second-term user. This requires a separate deployment mechanism or explicit product decision; do not assume the app's hidden metadata is a security boundary.

## Preflight on a Supabase branch

1. Confirm the migration account owns the existing `elite.is_enrolled()` function and the affected tables. A 2026-10-03 production catalog read found **19** policies on the five non-video content tables (the PRD says 18), plus `elite_videos_select`; the SQL snapshots the actual definitions. Check policy names, roles, commands, expressions, RLS enabled/forced flags, column types/defaults and `flow_configs_group_id_key` again immediately before applying. Resolve the Storage owner dependency above separately.
2. Count the roster: exactly 14 rows, 11 students, all cohort `1.0`, plus exactly ten videos as of 2026-10-03. The up script aborts if these invariants differ. Check there are no existing `elite_cohort_v1_backup` or `elite.cohorts` objects. Record row counts for all six content tables and confirm the named `elite_videos_select` policy exists.
3. Take a database backup and a separate export of the original RLS definitions. Run the up script on the branch. Inspect `elite_cohort_v1_backup.policies`, verify every old policy has a corresponding rewritten policy, and run the AC checks. Test the down script on a fresh branch clone before production planning.

## AC1: exact first-term visibility comparison

Use `scripts/cohort_v1_snapshot.py before --out <private-directory-outside-repo>` now, and the same command with `after` after migration; then `compare`. The script captures all **13** elite tables for each of the 11 existing students under `SET LOCAL ROLE authenticated` and `set_config('request.jwt.claims', …, true)` plus the subject claim, inside `BEGIN READ ONLY … ROLLBACK`. JSON rows are sorted by primary key and include row IDs plus all old column values. It removes only the cohort/status/common-material fields intentionally added or changed by the migration. The private directory contains student data and must never be committed or pasted into messages. Also inspect page queries at `/materials`, `/videos`, `/team/*`, `/flow`. Verify all 14 enrollment statuses are `active` and all 14 cohorts are `2026-1` before allowing app traffic. A live system can gain unrelated edits between snapshots; freeze writes for the comparison window or investigate each diff before declaring AC1 failed.

Then use two authenticated test users with the same `team_id` in different cohorts. Direct SQL reads and insert/update/delete attempts under their JWT context must prove that first-term content, including the ten videos and a known storage path, is hidden from the second-term student. Verify a suspended student gets zero rows from every elite table and cannot write or obtain a new signed URL; verify reactivation restores the exact original row sets. Existing signed URLs can remain valid for up to one hour. Verify instructors see both terms. Verify a common material and common video each appear for both terms. Verify concurrent `set_current_cohort()` calls never result in two current rows. Test a completely empty new term.

## Whether to pay for a Supabase branch

Production has only 18 recorded migrations dating from July 2026 while the shared QBC project began in January; replay alone may omit older base objects. A branch also has no student or Auth data, so it **cannot establish AC1**. AC1 uses the private production read-only snapshots above and a post-migration comparison.

A branch is still useful for exercising the complete up/down scripts against Supabase's real Auth, Storage, PostgREST, function ownership and RLS behavior. That value is conditional: first confirm the branch can be initialized with a schema-only production baseline (or an equivalent full schema clone) without touching production. Seed only synthetic accounts/data: one active instructor, first- and second-term students sharing a `team_id`, one suspended student, old and new rows in all six cohort-scoped tables, a `c_…` custom-chain flow config in each term, common material/video rows, and matching `storage.objects` test files. Test signed URL issuance, direct SQL reads, writes, unique keys and rollback guards. Do not import real student data.

Recommendation: authorize the paid branch only after the schema-baseline route is verified. If a complete baseline cannot be installed cheaply, use a local isolated Supabase stack seeded the same way for structural/RLS rehearsal, while retaining the production snapshots for AC1. No branch creation is part of this handoff.

## Rollback window

Run the down script only while all records still belong to `2026-1`, no material is marked common, no member is suspended, and roster membership matches the snapshot. The script restores saved policy and `is_enrolled()` definitions, original roster cohorts, original `flow_configs` uniqueness, and drops new columns/functions. If any guard fails, leave the database untouched and restore the snapshot or write a forward repair that preserves second-term data.
