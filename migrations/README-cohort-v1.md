# Cohort v1 handoff (production database unchanged)

Files: `20261002_cohort_v1_up.sql` / `_down.sql` for elite, and `20261002_cohort_v1_storage_up.sql` / `_down.sql` for Storage. Apply **main up → Storage up**; roll back **Storage down → main down**. Each file is transactional. The main down script deliberately aborts if second-term or suspended data exists, since returning to single-term RLS would disclose that data. In that case restore from the pre-migration database backup or prepare a data-preserving forward repair; do not force the down script. If Storage up fails, do not admit second-term users until it is fixed.

## Technical choices

1. Add `cohort` to each of `team_meetings`, `trade_ledger`, and `reviews`. The existing team number remains local to a cohort; `(cohort, team_id)` is the logical team key. This changes fewer app paths than adding a global teams table. Team queries and writes must be filtered by both fields. The RLS rules enforce both fields regardless of frontend filters.
2. Add `all_cohorts boolean` to `course_materials`. Ordinary materials match one `cohort`; a common item is visible to every active cohort. The upload form offers one mutually exclusive target-term selector, including `多期通用`. Upgrade to a mapping table only if specific subsets of terms become necessary.

`flow_configs` currently has a unique `group_id`. The migration changes uniqueness to `(cohort, group_id)`. **The updated app action must deploy with the SQL**: publishing now reads the current cohort and upserts on `cohort,group_id`; unpublishing filters by both. Without this app change, a second-term publish can overwrite or conflict with first-term settings. The SQL guard requires the old unique constraint to be present. The three team forms explicitly write the active member’s cohort, and their update paths filter by both cohort and team number. There are no team delete actions in this app. Roster writes expose cohort and status controls, and the admin team summary selects one cohort to avoid merging identical team numbers.

After rebasing onto the merged stage-six custom-chain implementation, `group_id` remains `sanitizeSplitConfig(payload).group`. For a custom chain this is its validated `c_…` chain ID, so the unique key is `(cohort, chain ID)`; the UI uses `resolveGroup(state)` for the same ID when choosing the current published config.

`course_videos` cohort isolation is included here to satisfy AC3: all links present at migration time move to `2026-1` (the 2026-10-03 read-only count was ten; recheck on launch night), and `elite_videos_select` applies the same cohort/common-material logic. Video v2 retains playback and per-video targeting UI. **Known AC8 limit accepted by the product manager:** suspension stops issuing new signed URLs immediately; URLs already issued by the materials page remain valid until their one-hour expiry. AC8 verification measures immediate denial of metadata/new URL issuance and records this one-hour existing-link window.

**Storage policy is required for AC3:** production's original `elite_materials_storage_select` checks `is_enrolled()` only. Because this policy also controls Storage `list()`, second-term members could enumerate first-term filenames and sign them. The separate Storage migration changes it to the approved predicate matching `storage.objects.name` to visible material metadata. A 2026-10-03 read-only check found exactly 11 metadata rows and 11 objects with 11 exact path matches, no prefix and no orphans. Although `storage.objects` belongs to `supabase_storage_admin` and `postgres` is not an owner-role member, the product manager confirmed that production `supautils.policy_grants` explicitly permits `postgres` to manage policies on `storage.objects` (and `storage.buckets`). Thus ownership alone does not block this `ALTER POLICY`. Use the established MCP `apply_migration` channel, as in migration `20260719035230` (`elite_materials_bucket`), so execution is recorded in `supabase_migrations`; do not infer this exception for other objects. The two Storage files use `ALTER POLICY` and avoid unrelated bucket changes. Storage up also snapshots bucket object names; Storage down refuses if any object was added or removed, including an orphan left after metadata deletion.

## Local rehearsal decision and result

Production has only 18 recorded migrations dating from July 2026 while the shared QBC project began in January; replay alone may omit older base objects. A branch also has no student or Auth data, so it **cannot establish AC1**. AC1 uses the private production read-only snapshots above and a post-migration comparison.

An isolated local Supabase stack exercises the complete up/down scripts against Supabase's real Auth, Storage, PostgREST, function ownership and RLS behavior. Initialize it with a schema-only production baseline (or an equivalent full schema clone) without writing to production. Seed only synthetic accounts/data: one active instructor, first- and second-term students sharing a `team_id`, one suspended student, old and new rows in all six cohort-scoped tables, a `c_…` custom-chain flow config in each term, common material/video rows, and matching `storage.objects` test files. Reproduce production's default ACL before applying the migration. Test signed URL issuance, direct SQL reads, writes, unique keys and rollback guards. Do not import real student data.

Product decision: **no paid branch**. On 2026-10-03 an isolated local Supabase Docker stack was seeded with synthetic identity claims/rows and an `elite-materials` bucket. Main up and Storage up both passed. Two students in different cohorts shared team 1 and custom-chain `group_id='c_abc123'`; direct RLS reads showed only each cohort's materials, videos, flow config and team rows, while instructor saw both. Actual Storage API calls with signed synthetic authenticated JWTs showed each student listed only their own file; signing the other cohort's known path failed; instructor could list and sign both. A suspended student listed zero files and could not obtain a new signed URL. A common material became listable/signable to both cohorts. Main down and Storage down each correctly refused while second-term data existed. After removing synthetic second-term data, Storage down then main down passed twice, restoring 14 original cohort values, original policy expression, ten videos and original unique group key. The private production snapshots remain the AC1 source of truth.

## Rollback window

Run the down script only while all records still belong to `2026-1`, no material is marked common, no member is suspended, and roster membership matches the snapshot. The script restores saved policy and `is_enrolled()` definitions, original roster cohorts, original `flow_configs` uniqueness, and drops new columns/functions. If any guard fails, leave the database untouched and write a forward repair that preserves second-term data. Full restoration of this shared QBC database is a disaster-only last resort requiring Jason and the QBC owner to agree.

## Frontend handoff

The admin cohorts page selects the current term; new roster members default to it. Instructor material and video uploads require explicit target-term selection, with one mutually exclusive `多期通用` option. The roster shows and edits each member’s term and status. Suspended members are sent to `/suspended`; the status RPC exists because RLS hides their enrollment row. Team updates filter by both team number and term. The published flow config action uses `(cohort, group_id)` and also requires explicit target-term selection; custom chain IDs remain `c_…`. After DB migration, deploy this frontend within minutes and test these paths. See `RUNBOOK-2026-10-13.md`.

The later local UI smoke test used only synthetic Auth accounts: the instructor switched current to `2026-2`, added a new member who landed in `2026-2`, suspended and restored that member, and uploaded a common material visible to both terms while the second term could not see the first-term file. A final up → Storage up → Storage down → main down cycle passed with the updated Storage object baseline guard. The local instance was returned to the pre-migration schema after the test.

## 2026-10-03 review fixes

Production's `pg_default_acl` for `elite` grants `authenticated=arwd` on new tables. The migration explicitly revokes that inherited whole-table ACL on `elite.cohorts` before granting read and limited insert/update columns; it also explicitly revokes and regrants execute on the four new functions. There are no new sequences in `elite`; indexes inherit table access, and the backup tables live in a private, separate schema. Local rehearsal now installs the same default ACL **before** main up, then verifies that an instructor's direct PostgREST PATCH of `is_current` gets HTTP 403 (`42501`). The earlier local stack lacked this ACL, so it could not reveal the privilege escalation; future rehearsals must model production default privileges, not only schema and RLS policies.

Instructor uploads and flow publishing require a target term with no preselection; the UI and server actions both reject omission. Materials and videos also offer one `多期通用` option that maps to `all_cohorts=true`; it is mutually exclusive with a specific term. Flow publishing selects a specific term and validates it server side; `flow_configs` has no `all_cohorts` column. Published flow rows, materials and videos show their term to instructors. Students may read `elite.cohorts` names through its read policy; this is an accepted product decision, with no cross-term content access granted by the names.
